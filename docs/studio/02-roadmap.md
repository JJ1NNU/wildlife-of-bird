# 로드맵 (출시까지)

> 관리: PM. 마일스톤마다 **관문(Gate)** 을 통과해야 다음으로 넘어간다.
> 관문 판정: QA 판정 리포트 → PM 정리 → 대표 승인.

## 1. 한눈에

GitHub 마일스톤 제목 = 아래 표의 "M + 이름" (예: `M4 두루미+공정성`). `scripts/setup-github.sh`와 같다.

|---|---|---|---|
| M0 | 착수 | 모두가 일할 수 있는 바닥을 깐다 | CI 통과, 대표 폰에서 열리는 미리보기 주소, 데이터 검증 동작, 화풍 결정 |
| M1 | 박새 수직 슬라이스 | 꾸밈 없는 UI로 박새를 여러 해 플레이 | 대표가 폰으로 박새 1년 이상 플레이하고 빨리 감기로 3년차 이후(계승·노화·게임 오버)까지 확인, 시뮬레이션 1,000판 무오류, 결정론 검사 통과 |

| M3 | 알파 | 보이는 게임, 친구 알파 | 박새 에셋·화면 마감, PWA 설치, 친구 알파 피드백 수집, S1 버그 0 |

## 3. 의존 관계와 병렬화

- **최우선 경로(critical path)**: ADR-001(엔진) → 스키마 v0 → 박새 엔진 → 시뮬레이터 → 박새 밸런스 → 두루미 → 4종 공정성 → 베타
- **M0부터 엔진과 병렬**: 디자인 명세, 콘텐츠 생태 데이터·글, 아트 화풍·와이어프레임, QA 지표 정의
- **ADR-001 이후 시작**: 클라이언트 웹 골격, 스키마에 맞춘 데이터 파일 정리
- **그림은 최우선 경로에 있지 않다**: 자리표시 그림으로 개발하고, M3 알파 전까지 박새 에셋만 완성한다.
- 클라이언트 화면 작업이 M3에 몰리지 않도록 M1부터 기능 UI를 쌓는다.
- PM은 현재 마일스톤의 P0가 70% 닫히면 다음 마일스톤 이슈를 미리 만든다.
- 각 마일스톤은 그 마일스톤의 산출물만 만든다. 다음 마일스톤을 위한 구현을 앞당겨 넣지 않는다(01-collaboration 15장).

## 4. 우선순위와 컷 라인

| 등급 | 1.0에서 | 항목 |
|---|---|---|
| P0 | 필수 | 4종, 총 번식 수 점수, 계승·짝 지시·육아 방침, 연간 자연 환경 변화(해거리·혹한·장마 등), 저장/이어하기, PWA, 통합 리더보드, 생태 정확성 |
| P1 | 목표 | 주간 시드 챌린지, 결과 공유 카드, 리플레이 검증, 세대를 넘는 지도 변화(천이 같은 자연 변화와 매립 같은 인공 사건), 칭호 전체 |
| P2 | 이후 가능 | 효과음·배경음, 업적 확장, 후속 종(기획서 10장), 다국어 |

일정이 밀리면 PM이 P2 → P1 순서로 컷을 제안하고 대표가 승인한다.

## 5. 관문 판정 절차

1. 관문 조건이 충족되었다고 보이면 PM이 `dept:qa` 이슈로 판정 요청.
2. QA가 `qa/reports/gate-M?.md`에 조건별 통과/실패와 근거 링크를 쓴다.
3. PM이 대표 보고에 판정 결과와 함께 `needs:ceo` "M? 관문 통과 승인" 요청.
4. 대표 승인 → PM이 "현재 마일스톤"을 갱신하고 회고를 `docs/studio/retros.md`에 기록.
5. PM이 마무리: `version.json`의 `gameVersion`을 `0.<M번호>.0`으로 올리는 PR 머지 → 태그 `v0.<M번호>.0` → GitHub 마일스톤 닫기. 남은 `P1`은 다음 마일스톤으로 옮기거나 `P2`로 내린다. M7(출시)은 `1.0.0`.
