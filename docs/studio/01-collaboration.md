# 협업 규칙 (모든 부서 공통)

> 관리: PM. 바꾸고 싶으면 `dept:pm` 이슈로 제안한다.
> 이 규칙만 지키면 각 부서가 자기 일만 해도 협업이 굴러가도록 설계되어 있다.

---

## 1. 조직

| 부서 | slug | 한 줄 임무 | 대표 산출물 |
|---|---|---|---|
| PM | `pm` | 출시까지 일이 끊기지 않게 흐름을 관리하고 막힘을 없앤다 | 로드맵, 이슈 보드, 대표 보고, 릴리스 |
| 게임디자인 | `design` | 규칙·수치·흐름의 주인. 기획서를 구현 가능한 명세로 바꾼다 | 기획서, 시스템 명세, `data/balance/` |
| 생태·콘텐츠 | `content` | 생태 정확성의 수호자이자 게임 글의 작가 | 종·이벤트·장소·도감 데이터, 출처 |

| 아트·UX | `art` | 시각 정체성과 사용 경험. 그림은 대표가 이미지 생성 AI로 만들고 아트가 지휘·후처리 | 아트 바이블, 와이어프레임, 에셋 |

## 2. 소통 채널

| 채널 | 무엇에 쓰나 | 주인 |
|---|---|---|
| GitHub 이슈 | 작업 요청, 결정 요청, 버그, 대표 작업. **부서 간 대화는 전부 이슈로** | 만든 사람 |
| Pull Request | 모든 변경. 리뷰 요청은 라벨로 | 작성 부서 |
| `docs/status/<부서>.md` | 부서의 현재 상태와 다음 근무를 위한 메모 | 각 부서 |
| `docs/status/README.md` | 스튜디오 전체 대시보드 | PM |
| `docs/studio/decisions.md` | 스튜디오 수준 결정 기록 | PM |
| `docs/adr/` | 기술 결정 기록(ADR) | 작성: 결정한 부서 / 관리: 엔진 |
| 고정 이슈 "📋 대표 보고" | 라운드마다 대표에게 보내는 요약 | PM |

다른 에이전트는 이 저장소만 볼 수 있다. 대화창에서 정한 것도 반드시 위 채널 중 하나에 남긴다.

## 3. 라벨과 마일스톤

| 묶음 | 라벨 | 뜻 |
|---|---|---|
| 부서 | `dept:pm` `dept:design` `dept:content` `dept:engine` `dept:client` `dept:art` `dept:qa` | 이 이슈를 **처리할** 부서 |
| 종류 | `type:task` `type:decision` `type:bug` `type:human` `type:question` | `type:human` = 대표가 손으로 해야 하는 일 |
| 대표 | `needs:ceo` | 대표의 결정이 필요 |
| 리뷰 | `review:pm` `review:design` `review:content` `review:engine` `review:client` `review:art` `review:qa` | PR에 그 부서의 리뷰가 필요 |
| 상태 | `status:blocked` `status:in-progress` | |
| 우선순위 | `P0` `P1` `P2` | P0 = 이번 마일스톤 필수, P1 = 이번 마일스톤 목표, P2 = 여유 있으면 |
| 심각도 | `sev:S1` `sev:S2` `sev:S3` `sev:S4` | `type:bug`에만 단다. 뜻은 `docs/agents/qa.md` 10장. 관문의 "S1 버그 0"은 이 라벨로 센다(02-roadmap 6장) |

- 마일스톤: GitHub 마일스톤 `M0 착수` ~ `M7 출시·운영`. 제목은 `02-roadmap.md` 1장의 이름 열과 정확히 같다.
- 라벨·마일스톤은 `scripts/setup-github.sh`로 만든다(PM 첫 근무).
- `type:human` 이슈에는 처리 부서 라벨 대신 **요청한 부서의 `dept:` 라벨**을 단다(결과를 받아 갈 부서).
- GitHub 기본 라벨(`bug`, `enhancement` 등)은 쓰지 않는다.

## 4. 근무 사이클 (모든 부서 공통)

세션 한 번 = 근무 한 번. 아래 순서를 지킨다.

1. **동기화** — 단일 폴더든 부서별 작업 폴더(`git worktree`)든 같은 명령을 쓴다.
   ```bash
   git fetch origin && git switch --detach origin/main
   ```
2. **읽기**: 내 임무 문서 → 이 문서(처음이거나 바뀌었을 때) → `docs/status/README.md` → 내 상태 파일
3. **받은 일 확인**
   - `gh run list --branch main --limit 1` — main의 CI가 실패 상태면 5장 1순위
   - `gh issue list --label "dept:<나>" --state open --limit 200`
   - `gh pr list --label "review:<나>" --limit 100` — 내 리뷰를 기다리는 PR
   - 내가 연 `type:decision`·`needs:ceo`·`type:human` 이슈에 답이 달렸는지
4. **고르기**: 5장의 우선순위대로. 한 근무에 1~3개, 끝낼 수 있는 크기로.
5. **일하기**: 이슈에 `status:in-progress`를 달고 브랜치를 만들어 작업한다(`git switch -c <부서>/<이슈번호>-<설명> origin/main`). 검증(테스트·데이터 검증·직접 확인)까지 끝낸다.
6. **넘기기**: PR을 열고 필요한 `review:*` 라벨을 단다(8장). 다른 부서가 이어서 할 일은 그 부서 라벨로 **새 이슈**를 만든다(완료 조건 포함).
7. **리뷰하기**: 나에게 온 리뷰를 처리한다(8장).
8. **마무리**: 내 상태 파일을 갱신해 main에 직접 푸시한다. 못 끝낸 일은 Draft PR로 올리고 이슈 댓글에 "어디까지 했고 다음은 무엇"을 남긴다.
   ```bash
   git switch --detach origin/main            # 작업 브랜치에서 빠져나와
   # docs/status/<부서>.md 수정 후
   git commit -am "[<부서>] 상태 갱신"
   git push origin HEAD:main || (git fetch origin && git rebase origin/main && git push origin HEAD:main)
   ```

세션이 짧게 끝나더라도 8단계는 반드시 한다.

**main에 직접 푸시가 막힌 환경**(세션이 자기 브랜치에만 푸시할 수 있는 경우)에서는 상태 파일도 PR로 올리고, 리뷰 없이 바로 스스로 머지한다.

## 5. 우선순위 규칙

1. **main이 깨졌다** (CI 실패) → 깨뜨린 PR의 작성 부서가 최우선으로 고친다. 발견한 부서는 그 부서 라벨로 `type:bug` `P0` 이슈를 연다. 원인 부서를 모르면 `dept:engine`.
2. **다른 부서를 막고 있는 일** — 나를 가리키는 `status:blocked`, 내 산출물을 기다리는 이슈
3. **나에게 온 리뷰 요청**
4. 현재 마일스톤 `P0` → `P1`
5. 다음 마일스톤 준비, `P2`

같은 단계 안에서는 오래된 것부터.

## 6. 이슈 쓰는 법

템플릿(`.github/ISSUE_TEMPLATE/`)을 쓴다. 다른 부서에 일을 맡길 때는 **완료 조건**을 반드시 적는다. 받는 부서가 질문 없이 시작할 수 있어야 한다.

- 제목: `[보내는부서→받는부서] 무엇을` — 예) `[design→engine] 짝 지시 수락률 공식 구현`
- 본문: 배경 / 할 일 / 완료 조건(체크박스) / 관련 문서·파일 / 의존·기한
- 라벨: `dept:<받는부서>` + `type:*` + `P*` + 마일스톤

---

## 7. 브랜치 · 커밋 · PR

- 브랜치: `<부서>/<이슈번호>-<짧은-설명>` — 예) `engine/12-seeded-rng`. 항상 `origin/main`에서 만든다.
- 커밋: `[engine] 시드 고정 난수 구현 (#12)`
- PR 제목: 커밋과 같은 형식. 본문은 PR 템플릿(무엇·왜·검증·영향받는 부서·스크린샷·잠정 처리).
- PR은 작게, 한 PR에 한 가지 목적. `Closes #12`로 이슈를 연결한다.
- 충돌은 작성 부서가 main에 맞춰(rebase) 해결한다.
- **main 직접 푸시 예외**(이 셋 말고는 전부 PR): 각 부서의 상태 파일, PM의 대시보드, 대표의 `assets/inbox/**` 업로드(대표는 GitHub 웹의 파일 업로드를 써도 된다).

## 8. 리뷰와 머지

모든 에이전트가 같은 GitHub 계정을 쓰므로 GitHub의 "Approve" 버튼은 쓸 수 없다. 대신 라벨과 댓글로 한다.

- **리뷰 요청**: 작성자가 `review:<부서>` 라벨을 단다.
- **승인**: 리뷰어가 `승인 (<부서>): 한 줄 요약` 댓글을 달고 **자기 `review:<부서>` 라벨을 뗀다**.
  - 예) `gh pr comment 34 --body "승인 (content): 생태 사실 이상 없음"` → `gh pr edit 34 --remove-label "review:content"`
- **수정 요청**: `수정 요청 (<부서>): …` 댓글로 구체적으로. 라벨은 그대로 둔다.
- **머지**: `review:*` 라벨이 하나도 없고 CI가 통과하면 **작성 부서가** 스쿼시 머지한다. 작성 부서의 세션이 끝났으면 PM이 머지할 수 있다.
- **CI가 아직 없을 때**(엔진의 첫 CI가 main에 들어가기 전): 작성 부서가 할 수 있는 검증을 직접 하고 PR 본문에 결과를 적으면 "CI 통과"로 본다.
- 리뷰는 다음 근무에서 최우선(5장 3순위)으로 처리한다.

### 부트스트랩 예외 (M0)
엔진의 **ADR-001(기술 스택), 저장소 뼈대, CI, 스키마 v0** PR은 모든 부서의 전제이므로 필수 리뷰를 기다리지 않고 엔진이 첫 근무 안에 머지한다. `review:*` 라벨 대신 관련 부서(client·design·content·qa)에 "머지 후 리뷰" 이슈를 연다. 각 부서는 다음 근무에 의견을 달고, 엔진은 그다음 근무에 반영한다(필요하면 ADR 개정).

### 필수 리뷰 표 (소유 부서가 아닌 부서가 작성했을 때)

| 바뀐 곳 | 필수 리뷰 |
|---|---|
| `data/balance/**` `data/calendar/**` `data/titles/**` | design |
| `data/species/**` `data/nodes/**` `data/predators/**` `data/codex/**` `data/text/**` | content |
| `data/events/**` `data/environment/**` | content + **design**(효과 등급 사용 확인 — 콘텐츠가 작성해도 design 리뷰 필수) |
| `packages/engine/**` `packages/sim/**` `scripts/data/**` | engine |
| `packages/schema/**` | engine + 그 데이터를 쓰는 부서(design·content·client). 호환이 깨지면 전 부서 공지 |
| 루트 설정·잠금 파일(패키지 매니저, tsconfig, 린트 등) | engine — 의존성을 추가하는 부서는 잠금 파일 변경을 포함해 `review:engine` |
| `apps/web/**` | client (눈에 보이는 화면이 바뀌면 art도) |
| `infra/**` `.env.example` | client |
| `packages/tokens/**` `assets/**` `scripts/art/**` | art (새·포식자 그림은 content도: 생태 정확성) |
| `docs/design/**` | design ([확정] 항목 변경은 `needs:ceo`) |
| `docs/content/**` | content |
| `docs/art/**` `docs/ux/**` | art |
| `qa/**` | qa |
| `docs/studio/**`(03-contracts 제외) `docs/agents/**` `CLAUDE.md` `README.md` `docs/README.md` `.gitignore` `version.json` `CHANGELOG.md` `.github/ISSUE_TEMPLATE/**` `.github/pull_request_template.md` `scripts/setup-github.sh` | pm (`CLAUDE.md`의 명령어·저장소 지도 섹션은 engine) |
| `docs/studio/03-contracts.md` `docs/adr/**` | engine |
| `.github/workflows/ci.yml` | engine / `.github/workflows/deploy.yml` → client |
| `docs/status/<부서>.md` | 그 부서만 고친다 |

- 각 부서는 자기 임무 문서(`docs/agents/<부서>.md`)를 직접 고치지 않고 PM에게 개정을 제안한다.
- 게임 플레이에 영향을 주는 PR은 QA에게 알린다(필수 리뷰는 아님, `dept:qa` 라벨의 확인 이슈로 충분).

## 9. 결정하는 법

| 단계 | 무엇 | 누가 | 어떻게 |
|---|---|---|---|
| **L1** 부서 결정 | 자기 소유 영역 안의 결정 | 그 부서 | 바로 결정하고 해당 문서·ADR에 기록 |
| **L2** 부서 간 결정 | 둘 이상의 부서에 영향 | 주 소유 부서가 결정, PM이 진행 | `type:decision` 이슈: 질문·선택지·추천·영향 부서. 관련 부서는 다음 근무에 의견을 단다. 의견을 받은(또는 한 라운드가 지난) 뒤 주 소유 부서가 이슈에 결정을 쓰고 닫는다. PM이 `decisions.md`에 옮긴다 |
| **L3** 대표 결정 | 기획서 [확정] 변경, 범위·일정의 큰 변경, 비용·계정, 외부 공개·출시, 화풍, 저작권·윤리 | 대표 | `needs:ceo` 라벨. 첫 줄에 추천안, 되돌릴 수 있는지 명시. PM이 대표 보고에 묶어 올린다 |

**기다리지 않기**
- 답을 기다리는 동안, 되돌릴 수 있는 일이면 추천안으로 **잠정 진행**한다. 코드·문서에 `잠정(#이슈번호)`를 남겨 결정이 바뀌면 찾아 고칠 수 있게 한다.
- 되돌릴 수 없는 일(데이터 삭제, 외부 공개, 비용 발생, 대표 계정 작업)은 기다리고 다른 일을 한다.

## 10. 대표와 일하는 법

- 대표는 사람이다. 시간이 가장 귀하다. 요청은 묶어서, 짧게, 추천안과 함께.
- `needs:ceo` — 결정 요청. 제목은 질문, 본문 첫 줄은 추천안.
- `type:human` — 대표가 손으로 할 일(이미지 생성, 계정 만들기, 비밀값 설정, 플레이테스트, 전문가 검수 의뢰). **예상 소요 시간, 단계별 방법, 결과물을 둘 곳**을 적는다.
- 대표 보고는 PM만 쓴다. 다른 부서는 대표에게 필요한 것을 이슈로 만들면 PM이 묶어 올린다.
- 대표가 이슈 댓글로 답하면 그것이 결정이다. 요청한 부서는 다음 근무에 반영하고, PM은 `decisions.md`에 기록한다.
- **닫기**: `needs:ceo` 이슈는 PM이 기록 후 닫는다. `type:human` 이슈는 결과를 받아 반영한 요청 부서가 닫는다.

## 11. 완료의 정의 (DoD)

- 이슈의 완료 조건을 모두 충족했다.
- CI 통과(타입체크·린트·테스트·데이터 검증·빌드 — ADR-001 이후 구체화).
- 새 규칙·데이터 형식·결정이 해당 문서에 반영되었다.
- 필수 리뷰 승인을 받았다(`review:*` 라벨 없음).
- 다른 부서가 이어서 할 일이 있으면 이슈로 넘겼다.
- 상태 파일을 갱신했다.
- 요구 범위를 넘는 구현·추상화·테스트가 없다(15장).

---

## 12. 안전 · 라이선스 · 윤리

- 비밀값(API 키 등)은 저장소에 넣지 않는다. `.env`는 커밋 금지, 형식은 `.env.example`로.
- 유료 서비스·결제는 대표 승인(L3) 없이 쓰지 않는다. 무료 등급 안에서 설계한다.
- 의존성은 MIT·Apache-2.0·BSD 등 허용적 라이선스만. 폰트는 OFL 등 자유 사용 라이선스.
- 글: 출처의 문장을 그대로 옮기지 않는다. 사실은 출처와 함께 우리 말로 쓴다.
- 그림: 프롬프트에 실존 작가 이름을 쓰지 않는다. 사진이나 남의 그림을 그대로 따라 그리게 하지 않는다. 사용한 도구·날짜·프롬프트를 기록한다.
- 개인정보: 리더보드에는 닉네임만. 이메일 등 개인정보를 모으지 않는다.
- 게임 속 생태 정보는 사실이어야 한다. 게임을 위한 의도적 타협은 기획서에 명시된 것만 허용한다.

---

## 13. 충돌 해결

1. 소유 영역 안에서는 소유 부서의 판단이 우선한다.
2. 부서 간 의견이 다르면 `type:decision` 이슈로 PM이 정리한다.
3. 그래도 안 되면 PM이 `needs:ceo`로 대표에게 올린다.

남의 영역을 몰래 고치지 않는다. 급하면 이슈를 열고 `P0`를 단다.

**문서끼리 내용이 다를 때의 우선순위**
대표의 최신 결정(이슈 답변·`decisions.md`) > 기획서(`docs/design/gdd.md`, 시스템 명세 포함) > `03-contracts.md`·ADR > `02-roadmap.md` > 부서 임무 문서 > 그 밖의 문서.
다른 것을 발견하면 우선순위가 높은 쪽을 따르고, 낮은 쪽 문서의 주인에게 고쳐 달라는 이슈를 연다.

## 14. 환경 메모

- **병렬 근무**: 부서마다 별도 세션(클라우드 세션 또는 로컬 `git worktree`)에서 일한다. 같은 부서의 세션을 동시에 두 개 열지 않는다. 4장의 git 명령은 두 방식 모두에서 동작한다.
- **근무 사이의 기억은 없다.** 저장소에 남긴 것만 다음 근무로 이어진다.
- **GitHub 접근은 필수**: 이슈·PR을 다룰 수 없는 세션(gh 미인증, GitHub 도구 없음)에서는 일하지 않는다. 할 수 있으면 상태 파일에 사유를 적고, 대표에게 보고하고 끝낸다.

## 15. 단순하게 만들기 (모든 구현 단계 — 대표 지시)

모든 부서, 모든 마일스톤, 모든 PR에 적용한다. 리뷰에서 위반을 발견하면 `수정 요청` 사유다.

**금지 1 — 확인되지 않은 요구에 대비한 선제적 복잡도**
- 기획서·명세·이슈의 완료 조건에 없는 기능, 추상화, 일반화, 설정 옵션, 확장 포인트를 "나중에 필요할 것 같아서" 미리 만들지 않는다.
- 예) 플러그인 구조, 범용 규칙 엔진, 아직 없는 종·플랫폼·다국어를 위한 일반화, 측정 없이 하는 성능 최적화, 친구 알파 전의 저장 마이그레이션 체계, 쓰이지 않는 데이터 필드, 미래를 위한 폴더·패키지·도구.
- 공통화는 두 번째 사례가 실제로 생겼을 때 한다.
- 확장이 필요해 보이면 구현하지 말고 이슈(`P2`)로 제안한다.

**금지 2 — 과도한 테스트**
- 테스트는 깨지면 게임이 틀리는 것만 지킨다: 결정론, 명세의 예시(공식·점수), 저장/불러오기 왕복, 데이터 검증, 핵심 흐름 e2e 스모크, 밸런스 측정.
- 버그를 고칠 때는 재현 테스트 1개를 남긴다.
- 하지 않는다: 모든 함수·화면·경우의 수에 테스트, 사소한 코드의 테스트, 구현 세부를 고정하는 스냅샷 남발, 같은 것을 여러 층에서 반복 검증, 오래 걸리는 테스트를 CI 기본 경로에 넣기.

**판단 기준**: "이것이 없으면 이번 이슈의 완료 조건을 채울 수 없는가?" — 아니면 만들지 않는다. 필요해지면 그때 만든다.
