# 시스템 명세 (specs/)

> 소유: 게임디자인. 모든 변경은 PR + `review:design`.
> 기준 문서는 기획서 `docs/design/gdd.md`다. **기획서와 명세가 다르면 명세가 최신이며, 같은 PR에서 기획서도 고친다.**
> 데이터 형식은 `docs/studio/03-contracts.md` 4장(엔진 소유)을 따른다.

## 이 폴더가 하는 일

기획서는 "무엇을 만드는가"를 사람의 말로 적는다. 이 폴더는 그것을 **엔진이 질문 없이 구현하고 QA가 그대로 테스트로 쓸 수 있는 규칙**으로 바꾼다.

숫자는 이 폴더에 두지 않는다. 숫자는 `data/balance/`에 두고, 명세는 그 **키 이름**으로 참조한다.
명세가 설명하는 것은 공식의 모양, 적용 순서, 경계 사례, 그리고 "왜 이 모양인가"다.

## 작성 규칙 (`docs/agents/design.md` 9장)

1. 모든 규칙에 예시 1개 이상 — **입력 → 출력**. 엔진과 QA가 그대로 테스트로 쓴다.
2. 경계 사례를 적는다(에너지 0, 짝 사망, 번식 중 사망, 계승 직후 겨울, 새끼 전멸 등).
3. 확률은 화면 표시 방법(반올림·범위)까지 적는다.
4. 숫자를 명세 본문에 박지 않는다. `data/balance/`의 키로 쓴다 (예: `energy.basalPerStep`).
5. 지금 마일스톤에 필요한 규칙만 적는다. 먼 미래(후속 종·다국어·확장)를 위한 일반화를 넣지 않는다(`01-collaboration.md` 15장).
6. 명세가 바뀌면 영향받는 부서(엔진·콘텐츠·QA·클라이언트)에 이슈를 연다.

## 용어 (전 명세 공통)

| 용어 | 뜻 |
|---|---|
| **런(run)** | 개체 생성부터 조작 개체 사망(게임 오버)까지. 점수가 매겨지는 단위 |
| **년(year)** | 런 안의 1년. 24시기 |
| **시기(period)** | 반 달. 1~24. `period 1` = 1월 상반, `period 24` = 12월 하반 |
| **단계(step)** | 플레이어가 행동 1개를 고르고 판정이 일어나는 최소 단위. 1시기는 1~3단계 |
| **국면(phase)** | 그 단계가 생애 주기의 어디인지 (`winter` `pairing` `incubation` 등). 이벤트 조건과 행동 목록이 이것으로 갈린다 |
| **결정(decision)** | 플레이어의 입력 1회. 기획서 4.2의 "결정 횟수"가 세는 단위 (00-core-loop 5장) |
| **조작 개체(actor)** | 지금 플레이어가 조작하는 새. 이 개체가 죽으면 게임 오버 |
| **번식(brood)** | 한 둥지(한배). 점수의 단위 (02-scoring) |
