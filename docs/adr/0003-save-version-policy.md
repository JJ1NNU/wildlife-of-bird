# ADR 0003: 알파부터 유지할 저장 버전 정책

- 상태: 제안 — 잠정(#542, M2 관문 승인 전 M3 미리 시작)
- 날짜: 2026-10-15
- 결정 부서: engine
- 리뷰: client (`apps/web/src/save.ts`가 이 정책을 따른다), qa (리플레이·결정론 관문)

## 맥락

- 지금은 `deserialize`가 `saveVersion`이 다르면 던지고, 화면이 문제 문구를 보여 준 뒤 새 게임을 시작한다(`03-contracts` 6장, 엔진 원칙 6). `SAVE_VERSION`은 M1~M2 동안 1 → 7로 올랐다.
- M3에서 **친구 알파**가 시작된다. 친구는 며칠에 걸쳐 한 판을 이어 하고, 그 사이 우리는 밸런스·이벤트·버그 수정을 계속 배포한다(main → 스테이징, `client.md` 3장). 배포마다 판이 날아가면 알파 피드백(오래 살아남은 판의 경험)을 못 모은다.
- 엔진 원칙 6: "알파 이후 형식이 바뀔 때부터 마이그레이션을 만든다". 이 ADR은 **언제부터·무엇을·못 하면 어떻게**를 정한다.
- 저장 문자열은 `{ saveVersion, state }` 하나이고 화면은 그대로 보관만 한다(`localStorage` 한 칸 `wb.run` + 선택 기록 `wb.choices`). 게임 데이터(`data/`)는 저장에 들어가지 않고 매번 새로 읽는다.
- 황금률 9: 지금 필요한 만큼만. 마이그레이션 틀을 미리 만들지 않는다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 지금처럼 — 버전이 다르면 늘 새 게임 | 엔진 일 없음 | 알파 중 배포마다 친구의 판이 사라진다 → 긴 판 피드백이 안 모임 |
| **B. 알파 기준 버전부터 한 단계씩 마이그레이션** (vN → vN+1 함수를 이어 붙임) | 친구 판이 배포를 넘어 이어진다. 바뀐 형식마다 작은 함수 하나 | 형식을 바꾸는 PR마다 마이그레이션 + 테스트 1개가 붙는다 |
| C. 저장 대신 선택 기록(`wb.choices`)을 새 엔진으로 다시 돌려 복원 | 형식 변환이 필요 없다 | 데이터·규칙이 바뀌면 같은 선택이 다른 판이 된다(결정론은 같은 버전 안에서만). 관문·이벤트가 달라져 기록이 중간에 막힌다 |

## 결정

**B**를 고른다. 세부 규칙:

1. **기준 버전**: 친구 알파 빌드를 처음 내보내는 PR(클라이언트 M3 #535 쪽, 알파 첫 배포)이 머지될 때의 `SAVE_VERSION`을 **알파 기준 버전**으로 정하고 `03-contracts` 6장에 적는다(엔진). 그 전까지는 지금처럼 던진다 — 마이그레이션을 만들지 않는다.
2. **형식이 바뀌면**(기준 버전 이후 `RunState` 필드를 더하거나·빼거나·뜻을 바꾸면): 그 PR이 `SAVE_VERSION` +1과 함께 `vN → vN+1` 마이그레이션 함수를 넣는다. `deserialize`는 저장 버전부터 지금 버전까지 함수를 차례로 적용한다. 새 필드의 값은 "그 기능이 없던 판"과 같은 뜻의 기본값으로 채운다(예: 없던 쿨다운 = 빈 객체).
3. **테스트**: 마이그레이션마다 테스트 1개 — 바로 앞 버전의 실제 저장 문자열(작은 fixture)을 읽어 지금 엔진에서 `getChoices`와 `act` 한 번이 오류 없이 돈다. 이것만 쓴다(깨지면 친구 판이 날아가는 것).
4. **데이터만 바뀌는 경우**(`data/balance` 수치·문구·이벤트 추가)는 형식 변경이 아니다 → 버전을 올리지 않는다. 저장된 판은 다음 결정부터 새 수치를 따른다. 단, **저장에 들어 있는 id**(이벤트·장소·종·칭호 등)를 지우거나 이름을 바꾸는 데이터 PR은 형식 변경으로 본다 → 엔진 리뷰에서 마이그레이션(바뀐 id로 옮기거나, 진행 중 이벤트면 그 관문을 닫기)을 붙인다.
5. **못 여는 경우** — 아래 둘은 지금처럼 던지고 화면은 "이 판은 이어갈 수 없어요 — 새 게임"을 보여 준다:
   - 저장 버전이 알파 기준보다 오래됨(알파 전 판)
   - 저장 버전이 지금보다 새것(배포를 되돌렸을 때)
   - 화면은 던진 저장 문자열을 바로 지우지 않고 새 게임을 시작할 때 덮어쓴다(지금 `save.ts` 그대로). 별도 백업 칸은 만들지 않는다.
6. **리플레이·결정론**: 리플레이(`npm run sim -- replay`, 플레이 기록 내보내기)는 **같은 게임 버전 안에서만** 같은 결과를 보장한다. 마이그레이션한 판의 기록은 리플레이 검사 대상이 아니다. 결정론 관문(QA 200판 저장/불러오기 왕복)은 그대로 — 같은 버전 왕복이다.
7. **끝**: 이 정책은 M7 출시 뒤에도 유지한다. 오래된 마이그레이션을 지우는 시점은 그때 새 ADR로 정한다.

## 결과

- 좋아지는 것: 알파 중 배포가 친구 판을 지우지 않는다. 데이터 튜닝(가장 잦은 변경)은 엔진 일 없이 그대로 배포된다.
- 감수하는 것: 기준 버전 이후 형식을 바꾸는 엔진 PR은 마이그레이션 함수 + fixture 테스트 1개만큼 커진다. 마이그레이션한 판은 리플레이 검증이 안 된다.
- 다른 부서가 해야 할 일:
  - client: 알파 빌드 첫 배포 PR에 엔진을 리뷰로 불러 기준 버전을 확정(#534 댓글로 알림). `save.ts`의 실패 문구를 5번 문구로(콘텐츠 UI 문구와 함께, 알파 화면 일에서)
  - design·content: 저장에 들어가는 id를 지우거나 바꾸는 데이터 PR에 `review:engine`(4번) — `03-contracts` 6장에 적는다
  - qa: 리플레이 검사는 같은 버전 기록으로만(6번)
